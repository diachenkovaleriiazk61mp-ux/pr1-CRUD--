## 1. Схема таблиці

Для варіанта 7 використовується сутність **«Запис про вакцинацію»**. Обов’язкові поля: код пацієнта, вакцина, серія, номер дози за схемою, дата введення та заклад. Фільтрація списку виконується за полем `vaccine`. Номер дози повинен бути від 1 до 4, а дата введення не може бути в майбутньому.

| Поле | Тип PostgreSQL | Обов’язковість | Пояснення |
|---|---|---|---|
| `id` | `BIGINT GENERATED ALWAYS AS IDENTITY` | PK | Ідентифікатор створює база даних; великий діапазон значень |
| `patient_code` | `VARCHAR(200)` | `NOT NULL` | Знеособлений код пацієнта |
| `vaccine` | `VARCHAR(200)` | `NOT NULL` | Назва вакцини; використовується для фільтрації |
| `batch` | `VARCHAR(200)` | `NOT NULL` | Серія може містити букви, цифри та початкові нулі |
| `dose_number` | `SMALLINT` | `NOT NULL` | Ціле значення від 1 до 4 |
| `administration_date` | `DATE` | `NOT NULL` | Потрібна лише календарна дата, без часу |
| `facility` | `VARCHAR(200)` | `NOT NULL` | Назва закладу вакцинації |

Первинний ключ автоматично створює індекс для `id`. Додатково створено B-tree індекс `(vaccine, id)`, оскільки список може фільтруватися за вакциною та сортується за `id`.

Повна схема:

```sql
CREATE TABLE IF NOT EXISTS vaccinations (
    id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    patient_code VARCHAR(200) NOT NULL CHECK (length(trim(patient_code)) > 0),
    vaccine VARCHAR(200) NOT NULL CHECK (length(trim(vaccine)) > 0),
    batch VARCHAR(200) NOT NULL CHECK (length(trim(batch)) > 0),
    dose_number SMALLINT NOT NULL CHECK (dose_number BETWEEN 1 AND 4),
    administration_date DATE NOT NULL CHECK (administration_date <= CURRENT_DATE),
    facility VARCHAR(200) NOT NULL CHECK (length(trim(facility)) > 0)
);
CREATE INDEX IF NOT EXISTS vaccinations_vaccine_id_idx ON vaccinations(vaccine, id);
```

## 2. Таблиця спроєктованого API

Для `POST` і `PUT` використовується JSON із шістьма полями:

```json
{
  "patient_code": "P007",
  "vaccine": "MMR",
  "batch": "B007",
  "dose_number": 1,
  "administration_date": "2026-01-10",
  "facility": "Clinic 7"
}
```

У відповідях створеного або отриманого запису додатково повертається `id`. `PUT` виконує **повну заміну** запису, тому всі шість полів є обов’язковими.

| Метод | Ендпоінт | Тіло/параметри запиту | Успішна відповідь | Помилки |
|---|---|---|---|---|
| `POST` | `/vaccinations` | JSON з 6 полями | `201`, створений запис з `id` | `400` — невалідні дані; `503` — БД недоступна |
| `GET` | `/vaccinations` | `limit`, `offset`, `vaccine` | `200`, `{items, total, limit, offset}` | `400` — невалідна пагінація; `503` — БД недоступна |
| `GET` | `/vaccinations/{id}` | без тіла | `200`, один запис | `404` — запис відсутній; `503` — БД недоступна |
| `PUT` | `/vaccinations/{id}` | повний JSON з 6 полями | `200`, оновлений запис | `400` — невалідні дані; `404` — запис відсутній; `503` — БД недоступна |
| `DELETE` | `/vaccinations/{id}` | без тіла | `204`, без тіла | `404` — запис відсутній або вже видалений; `503` — БД недоступна |
| `GET` | `/healthz` | без тіла | `200`, `{"status":"ready"}` | `503`, `{"status":"not_ready"}` |

Параметри пагінації: `limit=20` за замовчуванням, допустимий діапазон 1–100; `offset=0` за замовчуванням. Фільтр `vaccine` виконує точне порівняння. `GET /healthz` перевіряє доступність PostgreSQL запитом `SELECT 1`.

```yaml
  web:
    build: .
    image: vaccinations-pr1:local
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-vaccinations}:${POSTGRES_PASSWORD}@db:5432/${POSTGRES_DB:-vaccinations}
    networks: [backend]
    depends_on:
      db:
        condition: service_healthy
    cpus: 1.5
    mem_limit: 1g
    healthcheck:
      test: [CMD, /opt/venv/bin/python, -c, 'import urllib.request; urllib.request.urlopen("http://127.0.0.1:8000/healthz", timeout=2)']
      interval: 2s
      timeout: 3s
      retries: 30
    restart: unless-stopped
  lb:
    image: nginx:1.28.0-alpine
    ports: ['${PORT:-18080}:8080']
    volumes: ['./nginx.conf:/etc/nginx/nginx.conf:ro']
    networks: [backend, public]
    depends_on:
      web:
        condition: service_healthy
    restart: unless-stopped
networks:
  backend:
    internal: true
  public: {}
volumes:
  pgdata: {}
```

У стенді є три сервіси: `db`, `web` і `lb`. Зовні порт публікує тільки Nginx-балансувальник. PostgreSQL і вебінстанси працюють у внутрішній мережі. Кількість `web`-реплік змінюється параметром `--scale web=N`, без дублювання секції сервісу.

## 5. Вимірювання під навантаженням

Навантаження створюється власним скриптом `scripts/loadgen.py`. Генератор працює за принципом відкритого контуру: моменти відправки плануються заздалегідь за сіткою `t0 + i/rate`, а запити передаються пулу потоків, тому планування не повинно чекати попередньої відповіді.

Для кожної конфігурації виконувалось:

- інтенсивність 10, 100 і 500 запитів/с;
- 10 с прогріву;
- 30 с вимірювання;
- 3 повтори;
- у звіт заноситься медіана;
- тестовий запит: `GET /vaccinations/{id}`;
- перед серією у БД створюється 100 записів.

Приклад запуску генератора для 100 rps:

```bash
python scripts/loadgen.py http://127.0.0.1:18080/vaccinations/1 --rate 100 --warmup 10 --duration 30 --output results/run-100.json
```

Повна автоматизована серія:

```bash
python scripts/experiment.py --reset-lab-data
```

## 7. Висновок про межу інтенсивності та ефект другої репліки

При 10 і 100 rps сервіс утримував задану інтенсивність як з одним, так і з двома вебінстансами. Значення досягнутої інтенсивності практично збігалися із заданими, а частка помилок становила 0%.

На рівні **500 rps** задана інтенсивність вже не була досягнута:

- 1 інстанс: **118.900 rps**, p95 = **4694.576 мс**;
- 2 інстанси: **235.433 rps**, p95 = **4403.336 мс**.

Після додавання другої репліки пропускна здатність на цьому рівні зросла приблизно у **1.98 раза**. Спільними компонентами залишилися PostgreSQL, Nginx, мережа і ресурси хост-машини.

Водночас на 500 rps різко зріс scheduler lag самого генератора, оскільки скінченний пул потоків був зайнятий очікуванням відповідей. Тому результат 500 rps показує сумарну межу стенду та генератора на одній машині, а не лише межу вебсервісу.

## 8. Розрахунки за результатами серії

### 8.1. Прискорення і метрика Карпа–Флатта

Прискорення:

`S = X2 / X1`,

де `X1` — досягнута інтенсивність з одним інстансом, `X2` — з двома.

Для двох інстансів метрика Карпа–Флатта:

`e = (1/S - 0.5) / 0.5 = 2/S - 1`.

Для рівня 500 rps:

`S = 235.433 / 118.900 = 1.98010`.

`e = 2 / 1.98010 - 1 = 0.01005`.

Отже, при перевантаженні друга репліка дала майже двократний приріст. Значення `e ≈ 0.01` для цього вимірювання означає невелику ефективну нерозпаралелену частку за моделлю Карпа–Флатта. На рівнях 10 та 100 rps обидві конфігурації і так утримували заданий потік, тому `S≈1` там пояснюється недостатнім навантаженням, а не відсутністю користі від масштабування.

### 8.2. Перевірка закону Літтла

Закон Літтла:

`L = λ · W`.

Перевірка виконана для 100 rps при одному інстансі:

- `λ = 99.90000 rps`;
- `W = 0.0315393 с`;
- `λW = 99.90000 × 0.0315393 = 3.1507735`;
- виміряне `L = 3.1448236`.

Розбіжність:

`|3.1448236 - 3.1507735| / 3.1507735 × 100% = 0.189%`.

Отримана мала розбіжність підтверджує узгодженість вимірювань із законом Літтла.

### 8.3. Порівняння відкритого і закритого контурів

Для порівняння використано рівень 500 rps, де сервіс вже не утримував задану інтенсивність.

| Режим | Досягнуто, rps | p95, мс |
|---|---:|---:|
| Відкритий контур | 118.900 | 4694.576 |
| Закритий контур | 133.433 | 4254.680 |

У закритому контурі новий запит надсилається після завершення попереднього в межах фіксованої кількості одночасних запитів. Через це при перевантаженні потік автоматично зменшується і черга не накопичується так швидко. Саме тому p95 у закритому контурі виявився меншим, хоча сам сервіс не став швидшим.

## 10. Виконання додаткової вимоги варіанта

Для варіанта 7 фінальна стадія повинна використовувати `debian:12-slim`, а базовий образ має бути зафіксований **digest**, а не лише тегом.

У Dockerfile обидві стадії починаються з:

```dockerfile
FROM debian:12-slim@sha256:7c7b2c966bc9ee8cedfeef67e0e279108992c77681fa595db4a9d65c06ccc587
```

Тобто конкретний базовий шар зафіксований SHA-256 digest. Повторна збірка порівнювала базові `RootFS.Layers`; використано той самий базовий шар.

Підтвердження збережені у:

- `results/image.json`;
- `results/build-first.log`;
- `results/build-second.log`.

Ліміти вебконтейнера також відповідають варіанту: **1.5 CPU** та **1 GB RAM**.

## 11. Відкинуті рішення

1. **SQLite замість PostgreSQL.** Відкинуто, оскільки умова прямо вимагає PostgreSQL, а дві вебрепліки повинні працювати зі спільною базою.
2. **Зберігання даних у словнику Python.** Відкинуто, тому що дані втрачались би після перезапуску і не були б спільними для реплік.
3. **Окремий сервіс `web2` у docker-compose.yml.** Відкинуто, оскільки кількість інстансів за умовою повинна змінюватися параметром запуску (`--scale`), без копіювання секції сервісу.
4. **Навантаження тільки фіксованою кількістю віртуальних користувачів.** Відкинуто, тому що це закритий контур, який зменшує фактичний потік при зростанні затримки і може приховати перевантаження.
5. **`FROM debian:12-slim` тільки за тегом.** Відкинуто, оскільки тег може вказати на інший образ після оновлення і не виконує додаткову вимогу варіанта 7.

## Загальний висновок

У практичній роботі реалізовано CRUD-сервіс для записів про вакцинацію відповідно до варіанта 7. Сервіс працює з PostgreSQL, має необхідні шість ендпоінтів, валідацію, пагінацію та фільтрацію за вакциною. Стенд розгортається через Docker Compose і складається з бази даних, масштабованого вебсервісу та Nginx-балансувальника.

При 10 і 100 rps сервіс стабільно утримував задану інтенсивність. На 500 rps було зафіксовано перевантаження; додавання другої вебрепліки збільшило завершену пропускну здатність з 118.900 до 235.433 rps. Виконано розрахунок прискорення та метрики Карпа–Флатта, перевірку закону Літтла і порівняння відкритого та закритого контурів. Додаткова вимога варіанта щодо фіксації `debian:12-slim` за digest виконана.

## Додаток А. Конфігурація Nginx

```nginx
events { worker_connections 4096; }
http {
    resolver 127.0.0.11 valid=2s ipv6=off;
    log_format instances '$time_iso8601 $request $status upstream=$upstream_addr';
    access_log /dev/stdout instances;
    upstream api {
        zone api 64k;
        server web:8000 resolve;
        keepalive 64;
    }
    server {
        listen 8080;
        location / {
            proxy_pass http://api;
            proxy_http_version 1.1;
            proxy_set_header Connection "";
            proxy_connect_timeout 3s;
            proxy_read_timeout 60s;
        }
    }
}
```
